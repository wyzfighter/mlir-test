## 2. 每一项新增的作用与生效方式

### 2.1 `Passes.td` 的定义（+7 行）

**作用**：声明 pass 的名字、锚点、依赖方言。

```tablegen
def ConvertOpenACCToOpenMPPass : Pass<"convert-openacc-to-openmp", "ModuleOp"> {
  let summary = "Convert the OpenACC ops to OpenMP ops";
  let dependentDialects = ["omp::OpenMPDialect", "acc::OpenACCDialect"];
}
```

**生效方式**：TableGen 由这一段生成三样东西，分处 `Passes.h.inc` 的三个宏段：

| 生成物 | 宏开关 | 内容 |
|---|---|---|
| 声明 | `GEN_PASS_DECL_CONVERTOPENACCTOOPENMPPASS` | `createConvertOpenACCToOpenMPPass()`、`registerConvertOpenACCToOpenMPPass()` |
| 实现基类 | `GEN_PASS_DEF_CONVERTOPENACCTOOPENMPPASS` | `mlir::impl::ConvertOpenACCToOpenMPPassBase<T>` |
| 注册函数体 | `GEN_PASS_REGISTRATION` | `inline void registerConvertOpenACCToOpenMPPass()` |

**锚点是 `ModuleOp` 而非 `func::FuncOp`**，这一点是效果的前提：输入是 `llvm.func`，而现有 acc pass 锚在 `func::FuncOp`（`ACCSpecializeForHost.cpp:334`），锚 FuncOp 将覆盖不到目标函数。

### 2.2 头文件（28 行）

**作用**：把生成的声明暴露给使用方。

**生效方式**：

```cpp
#define GEN_PASS_DECL_CONVERTOPENACCTOOPENMPPASS
#include "mlir/Conversion/Passes.h.inc"
```

这一段只展开"声明"宏，避免把实现也拖进来。同时导出 `populateOpenACCToOpenMPConversionPatterns(RewritePatternSet&)`，使 pattern 可被单独复用或测试。

### 2.3 实现文件（208 行）

**作用**：这是唯一产生"效果"的地方——把 acc compute 语义在 MLIR 层换成 omp 语义，从而接入已有的 omp 降级链路。

**生效方式**（三个组成部分）：

| 位置 | 内容 | 生效机制 |
|---|---|---|
| `:47-76` | `normalizeDataClauses` | 在**即将被消费的 region 内**把 `acc.private` / `firstprivate` / `reduction` 的结果替换为 host 变量；类型不一致则跳过 |
| `:78-163` | `ConvertParallelWithLoop` | 匹配 `acc.parallel`，提升前置算子，构造 `omp.parallel` / `omp.wsloop` / `omp.loop_nest`，搬运 region，改 terminator |
| `:172-207` | pass 主体 | `applyPatternsGreedily` 驱动 pattern；随后按符号引用清理失去用户的 recipe |

关键的**语义替换**在于：`acc.parallel combined(loop)` 与 `acc.loop combined(parallel)` 一起被消费掉，产出的 `omp.parallel` 由此具备完整的目标语义（线程组 + 可分工循环），后续不需要任何 OpenACC 侧的语义信息。

### 2.4 `Passes.h` 与 `fir-opt.cpp`（+5 / +2）

**作用**：让两个工具都能看到这个 pass。

**生效方式**：两条注册路径不同，这是踩过的一个点。

```text
路径一（mlir-opt）
  add_mlir_conversion_library(MLIROpenACCToOpenMP ...)
       │  写入全局属性
       ▼
  MLIR_CONVERSION_LIBS
       │
       ▼
  MLIRRegisterAllPasses  ──→  mlir-opt 自动带上
  → 只需在 Passes.h 里 include 新头（+5 行）

路径二（fir-opt）
  fir-opt 不走 registerAllPasses()
  （InitFIR.h:107 的 registerMLIRPassesForFortranTools 只注册子集）
       │
       ▼
  必须在 fir-opt.cpp:46 显式调用 registerConvertOpenACCToOpenMPPass()
  （并在 :15 include 新头）
```

### 2.5 两个 CMake 改动（+1 / +1）

**`mlir/lib/Conversion/CMakeLists.txt:52`** —— 加 `add_subdirectory(OpenACCToOpenMP)`。

**生效方式**：没有这一行，`MLIROpenACCToOpenMP` 目标根本不会被创建，`add_mlir_conversion_library` 里的注册也不会写入 `MLIR_CONVERSION_LIBS`。**这是最容易漏、且症状最隐蔽的一处**：CMake 不报错，只是 pass 不出现。

**`flang/tools/fir-opt/CMakeLists.txt:52`** —— 链接 `MLIROpenACCToOpenMP`。

**生效方式**：`createConvertOpenACCToOpenMPPass()` 的定义在被 `GEN_PASS_DEF` 展开的那个 TU 里（即本库），所以 fir-opt 必须链接它，否则 undefined symbol。

## 3. 达成效果的完整链路

三条链，缺一不可。

### 3.1 注册链（pass 能被找到）

```text
Passes.td:1047-1050
   │  tablegen
   ▼
Passes.h.inc（三个宏段）
   │  Passes.h:60-64 include
   ▼
fir-opt.cpp:15 include / :46 显式调用
mlir-opt（经 MLIRRegisterAllPasses 自动获得）
   │
   ▼
--help 中可见 convert-openacc-to-openmp
```

### 3.2 转换链（acc 语义变成 omp 语义）

```text
fir-opt（driver：MlirOptMain）
   │
   ▼
PassManager 调度 ConvertOpenACCToOpenMPPass
   │
   ▼
runOnOperation()                              OpenACCToOpenMP.cpp:174
   │
   ▼
applyPatternsGreedily（top-down）
   │
   ▼
ConvertParallelWithLoop::matchAndRewrite      OpenACCToOpenMP.cpp:79
   ├── normalizeDataClauses                    同文件 :47（调用点 :100）
   ├── 提升前置算子
   ├── 构造 omp.parallel / omp.wsloop / omp.loop_nest
   ├── 搬运 region、acc.yield → omp.yield
   └── 擦除 acc.loop / acc.parallel
   │
   ▼
产物：omp.parallel { omp.wsloop { omp.loop_nest { ... } } omp.terminator }
```

**这一步是"效果"的来源**：转换之后 IR 里不再有 compute 类 acc 算子，因此后续翻译不再碰到 `unsupported` 分支。

### 3.3 翻译链（omp 语义变成运行时调用）

```text
mlir-translate / tco
   │
   ▼
ModuleTranslation::convertOperation            ModuleTranslation.cpp:996 / :1005
   │  iface.getInterfaceFor(&op)  按算子所属方言选接口
   ▼
OpenMPToLLVMIRTranslation
   ├── convertOmpParallel       :3101  → OpenMPIRBuilder::createParallel
   │                                     （声明 OMPIRBuilder.h:795）
   │                                     → __kmpc_fork_call
   ├── convertOmpWsloop         :2891  → 静态分工循环
   │                                     → __kmpc_for_static_init_4u
   │                                     （枚举在 OMPIRBuilder.cpp:5328）
   └── convertOmpLoopNest       :3498
   │
   ▼
LLVM IR：__kmpc_fork_call + __kmpc_for_static_init_4u → libomp
```

**方言分派是关键机制**：`iface.getInterfaceFor(&op)` 按算子所属方言选择翻译接口，所以 `omp.*` 与残留的 `acc data` 可以在同一函数里各走各的接口。这正是"A+B 混合"能成立的基础。

## 4. 实测效果

### 4.1 注册效果

```bash
/home/wangyz/.llvm/build-dcc/bin/fir-opt  --help | grep convert-openacc-to-openmp
/home/wangyz/.llvm/build-dcc/bin/mlir-opt --help | grep convert-openacc-to-openmp
```

两个工具各命中 1 次，pass 名与 summary 正确显示。

### 4.2 转换效果

输入 —— 转换前关键结构（`/home/wangyz/test/openacc/acc_loop/try.fir.mlir`，源程序 9 行 Fortran，`do ThisIsIterater = 3, 98`）：

```mlir
acc.parallel combined(loop) {
  %3 = acc.private varPtr(%2#0) recipe(@privatization_ref_i32) -> !fir.ref<i32>
  acc.loop combined(parallel) private(%3) control(%iv: i32)
      = (%c3_i32) to (%c98_i32) step (%c1_i32) {
    fir.store %iv to %4#0
    acc.yield
  } attributes {inclusiveUpperbound = array<i1: true>, independent = [...]}
  acc.yield
}
```

输出 —— 转换后：

```mlir
omp.parallel {
  omp.wsloop {
    omp.loop_nest (%arg0) : i32 = (%c3_i32) to (%c98_i32) inclusive step (%c1_i32) {
      fir.store %arg0 to %3#0 : !fir.ref<i32>
      omp.yield
    }
  }
  omp.terminator
}
```

可观察到的三个变化：

| 变化 | 说明 |
|---|---|
| `acc.private` 消失 | 被归一化，其结果替换为 host 变量 |
| `acc.private.recipe` 消失 | 符号引用消失后被清理，不再阻塞翻译 |
| `acc.yield` → `omp.yield` | terminator 按目标方言补齐 |

产物中 `acc.` 残留计数为 0。

### 4.3 运行时符号效果

```bash
fir-opt --convert-openacc-to-openmp /home/wangyz/test/openacc/acc_loop/try.fir.mlir \
  | tco -o try.ll
grep -E "__kmpc_fork_call|__kmpc_for_static_init" try.ll
```

```text
call void (ptr, i32, ptr, ...) @__kmpc_fork_call(ptr @1, i32 1, ptr @_QQmain..omp_par, ptr %structArg)
call void @__kmpc_for_static_init_4u(ptr @1, i32 ..., i32 34, ptr %p.lastiter, ...)
declare void @__kmpc_for_static_init_4u(...)
declare !callback !9 void @__kmpc_fork_call(...)
```

共 4 处命中（2 处调用点 + 2 处声明）。附加验证：

| 检查 | 结果 |
|---|---|
| `llvm-as try.ll -o /dev/null` | OK |
| 循环语义 | 归一化后 `lb=0, ub=95, step=1` → 96 次迭代，与源 `3..98` 闭区间一致；IV 反归一化为 `iv+3` |
| 闭区间传递 | 输出带 `inclusive`，未做 `ub+1` |
| 幂等 | 连跑两次 pass，exit=0，stderr 空 |
| 两条插入位置 | 高层 FIR 与已降到 LLVM 层的 IR 均通过 |

**结论：`acc.parallel loop` 的 compute 语义已被成功替换为 OpenMP 语义，并端到端落到 libomp 的运行时调用上。**

## 5. 未达成的效果

这一节必须与上一节同等醒目。

### 5.1 未落在 DCU 上

达成的是**主机并行**，不是设备并行。三条依据：

1. 产物中 `omp.target` 计数为 0；
2. 产出的是 12 处 `__kmpc_*`（libomp 主机运行时），outline 出的是 host 函数 `_QQmain..omp_par`；
3. `OpenACCToLLVMIRTranslation.cpp` 的全部 runtime 调用点（`:65` / `:69` / `:73` / `:273` / `:276`）**只有 data mapper，没有一处 `__tgt_target_kernel`**，即 A 路线本身没有发射设备 kernel 的出口。

而完成度指标要求「并行部分必须最终在 DCU 上并行运行」。**当前不满足。**

### 5.2 存在一个语义矛盾

数据路径的三个 mapper 调用传的 device id 是 `kDefaultDevice`：

```text
OpenACCToLLVMIRTranslation.cpp:45     static constexpr int64_t kDefaultDevice = -1;
同文件 :371 / :414 / :467             emitMapperCall(..., kDefaultDevice, totalNbOperand);
```

`-1` 在 OpenMP offload ABI 里表示默认设备（此判断为源码推断，**未在 DCU 上做运行时验证**）。因此对含真实 data clause 的程序，会出现"数据提交给默认设备、计算跑在主机"的情形。

当前测试用例没有 data clause，所以未暴露。

### 5.3 私有化语义是简化

`normalizeDataClauses` 把 per-thread 私有副本替换为 host 变量。本用例中 `ThisIsIterater` 的存储实际落在共享位置，**存在数据竞争**。这是 MVP 的已知取舍，真正的私有化需要 recipe 展开（alloca + init region + 每迭代独立存储）。

### 5.4 覆盖范围有限

仅覆盖 `acc.parallel` + `acc.loop`。`acc.serial` / `acc.kernels` / reduction / collapse 均未覆盖。
